# BiliTouch 0.2.11

发布日期：2026-11-08。

## 动态页：底部那枚「加载更多」删掉了

它在页面底部常驻，跟"列表滚到哪"没有关系（挂的是 `DockPanel.Dock="Bottom"`，永远贴在窗口底边），
而滚到底本来就会自动补下一页。两件事叠起来，它就成了一个"一直在、但点不出新内容"的杂项。

现在底部只留两件事：正在自动加载的转圈、「已经到底啦」。
首页当初删「加载更多」也是同一个理由，两边现在一致了。

## 刷动态刷一会就提示「网络请求过于频繁」

`-412 request was banned` 是 B 站按 **IP 算总请求密度**的限流，跟账号无关。
原来的请求密度在四个地方失控，逐个处理：

**1. 未读状态把整个关注列表翻完**
`portal` 接口带 `up_list_more=1` 时关注列表是分页的，原实现每次都把后面的页全部翻完
（关注 200+ 人 ≈ 7~8 次请求），而定时轮询每 45 秒就调一次 —— 光"什么都不做"每分钟就要十几次请求。
现在分两档：进页面 / 手动刷新 / 标记已读走**全量**；**定时轮询只读第一页**。

**2. 找新动态时往下翻 4 页**
轮询只需要"有没有新东西"这个粗结论，不需要精确条数。轮询档只读第一页。

**3. 滚动加载没有在途闸门**
`ScrollChanged` 是按帧来的，触底那几帧会连着发起同一个翻页请求。
左右两栏都补上 `Loading / LoadingMore / HasMore` 判断。

**4. 被限流之后越打越多**
原来命中 -412 只做"这一次退避重试"，是正反馈。
现在有一个进程级令牌桶：所有出站请求先过闸；命中 -412 时把整个桶**关掉一段时间**，
这段时间内一个请求都出不去，客户端才可能真正等到服务端放宽（实测 45~180 秒恢复）。

阈值取 **24 突发 / 12 每秒**（上限 720 次/分钟）。一开始取的是 12 / 6，实测正常运行也会变慢 ——
病根在上面那几处循环，桶只需要当安全带，不需要当刹车片。

## 验证

- 回归 13 个套件、**454 项检查全绿**，其中新增 `rate-limit` 13 项。
- 其中一条是源码扫描护栏：`ApiClient*.cs` 里每一处 `_http.SendAsync` 往上 3 行必须有
  `ThrottleAsync` —— 以后新加接口也绕不过限速。
- 另两条把"重试要有上限"和"轮询走省额度档"钉住。
- 上一版的全屏闪退与黑屏修复未受影响：`--verify-fullscreen --rounds=6` 通过、`0×0` 出现 0 次。
