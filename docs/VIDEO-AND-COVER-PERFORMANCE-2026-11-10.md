# 视频硬解与封面性能检查（2026-11-10）

检查基于仓库 `41a2b96` 之后的工作树。用户正在运行的安装版为 `0.2.18-fix1+2c3dd8a`；本次修改只写入源码和本地构建，没有覆盖安装版，也没有发布。

## 视频：合成输出此前没有充分使用硬件解码

本机配置 `HardwareAccelerationEnabled=true`、`UseVmemRenderer=true`，运行日志包含 `[Vmem] mounted: video host = VmemVideoView`。前者控制 WPF 页面渲染；后者用内存帧参与 WPF 合成，以实现圆角、阴影与连续变形。

LibVLC 3 的 `libvlc_video_set_callbacks` 会把播放器的 `avcodec-hw` 设置为 `none`。原来的播放器没有在这条正常构造路径上显式请求硬解。LibVLCSharp 的 `EnableHardwareDecoding=true` 会给媒体加入 `:avcodec-hw=d3d11va`，实测可以恢复合成输出的硬解。不能用原生 VideoView 以前留下的 D3D11VA 日志，证明当前合成窗口正在硬解。

现在在宿主/回调挂载后明确请求硬件解码。用同一份 3840×2160、60 fps 本地 H.264 动态夹具，日志确认 `using hw decoder module "d3d11va"`，并报告 Intel Arc B390。该机器也有 RTX 3080；本次测试没有强制选择独显。

|阶段|帧交付/秒|WPF 上传/秒|CPU 毫秒/秒|
|---|---:|---:|---:|
|原合成路径，未明确请求硬解|39.8|39.8|2055|
|原拷贝实现，明确请求硬解|56.2|56.2|1780|
|硬解 + 缓冲交接优化的一轮测量|59.5|59.5|1808|
|最终不透明格式的一轮测量|49.5|49.0|1273|

这些是短时夹具的帧交付/上传计数，不是显示器实际呈现率。复测存在波动，不能据此承诺所有 4K 视频稳定 60 fps。早期未请求硬解时，VLC 回调的协商尺寸还出现过 3840×2178；启用硬解后的协商尺寸为 3840×2160。

本次同时完成：

- 默认启用合成输出；移除设置页开关及其持久化字段，旧配置中的 false 不再关闭合成。原生输出只保留为内部诊断对照。
- 将解码缓冲与待显示缓冲交换，省掉视频线程上的一次全帧拷贝。4K 每帧约减少 31.6 MiB 的应用层拷贝，WPF 上传仍需一次拷贝。
- 按 RV32 的不透明 BGRX 语义使用 Bgr32 位图，避免把未定义的第四字节当作透明度。
- 隐藏视频时跳过上传；恢复显示时补上最后一帧。
- 位图暂时不可写时以单个低优先级计时器重试；新帧状态在缓冲锁内更新，避免暂停前最后一帧丢失。
- 切换画质增强设置时保留原合成内核，不把合成回调接到另一份原生输出内核。

这里仍有颜色转换、显存读回和 WPF 上传开销，尚未实现显卡共享纹理直接合成；厂商超分的原生 D3D11 输出也不能等同于合成输出。不能称为全程零拷贝。

参考：[LibVLC 3 回调实现](https://github.com/videolan/vlc/blob/3.0.x/lib/media_player.c#L1018)、[LibVLCSharp 3.8.0 的硬解选项](https://github.com/videolan/libvlcsharp/blob/3.8.0/src/LibVLCSharp/Shared/MediaConfiguration.cs)、[LibVLC 内存输出的性能限制](https://github.com/videolan/vlc-3.0/blob/master/include/vlc/libvlc_media_player.h)。

## 封面：模糊缓存与重复解码已修，首页整体掉帧尚未解决

首页、搜索视频结果和历史记录均使用 `VideoCard`，封面走同一个 `CoverLoader`；并没有为搜索、历史专门设定低画质。首页与历史使用视口虚拟化，搜索视频结果当前使用非虚拟化卡片面板，列表生命周期不同。

确认的两个问题：

1. 缓存查找只要找到同 URL 的任意尺寸就返回，最小档位甚至可以代替大卡片或原图预览。先缓存小缩略图后，大图请求会被小图截住。现已仅允许同档、更大档或完整原图满足请求，小图需要重新从已缓存的源文件解码。
2. 225% DPI 下的 720/960 档封面，每张约 1.1/2 MiB。原来的 32 MiB 预算只能容纳十几至二十几张，无法覆盖约 40 张已实现卡片和多个预热页签。运行时内存额度至少 4 GiB 时将强缓存预算提高到 96 MiB，较低额度仍为 32 MiB；保持按字节及条数淘汰。完整窗口复测第二轮的新封面加载计数从 7–8 次降到 0 次。

另补齐了 OnLoad 解码后的文件流/内存流释放。保留按尺寸后台解码、并发上限、视口加载、较大图复用与 Fant 高质量缩放。

### 完整窗口与单独卡片墙的结果不同

225% DPI、110% 应用缩放的单独 HomePage 夹具，屏幕采样的滚动变化率约 74–88 次/秒。降低采样质量或移除整卡缓存没有稳定收益，未将这些降画质方案写入产品。

完整 MainWindow 同类测量约 34–43 次/秒。关闭封面后，UI 线程仍有约 50 MiB/3 秒的分配和明显负担；隐藏顶部装饰、关闭皮肤或改变应用缩放也未消除低帧率。空白封面会使屏幕条带采样更容易重复，不能直接把其画面变化率当作真实 FPS。

因此，封面有可确认的重复工作，但它不是完整首页低帧率的唯一原因。缓存优化减少了重复加载与部分 GC，尚未稳定提高完整窗口的滚动帧率。采样中能看到文字布局、卡片实现和自动化树更新；目前证据不足以认定其中某一项为主因，后续应继续针对完整窗口分析，不能只用独立卡片墙结果验收。

采样记录在 `artifacts/touch-tests/cover-performance-before.log`、`home-window-performance.log`、`home-main-fast.log`、`home-main-after.log`。较小的可视化实现批次在对照中没有稳定收益，已恢复原批次策略。

## 验证

Release 构建通过，保留已有编译警告；8 组定向验证共 131 项通过。验证使用隔离的数据目录，没有改写用户的账号或观看历史。

- 封面尺寸升级、原图请求、较大图复用、回滚复用、取消过期解码。
- 新默认值与旧配置迁移；多帧交接、像素完整性、隐藏/显示、格式清理后的排队回调、资源释放。
- 真实 PlayerWindow 硬解请求与合成宿主；连续缩放、停靠圆角、往返、最小化与恢复、布局切换；播放器各滚轮区域。
- 4K60 夹具的协商尺寸、变化画面、上传与截图、圆角裁剪。帧率仅代表短时测试，不代表在线 AV1/HEVC、HDR 或长时间高负载均已验收。

最终 4K 视图验证在 900×560 的窗口中测得交付 56.0 帧/秒、上传 55.3 次/秒，圆角截图与变化画面检查均通过；它与前表 1280×820 窗口的负载不同，应分别解读。

详细日志为 `artifacts/touch-tests/performance-*.log` 及 `vmem-4k-*.log`。本地可运行构建为 `BiliTouch/bin/Release/net10.0-windows/BiliTouch.exe`，需保留其旁边的依赖文件。
