# 0.2.3 性能排查（2026-11-06）

用户现象：打开客户端后各处都卡，不限于视频播放。此轮只排查，没有修改应用业务代码，也没有修改显卡、显存或用户配置。

## 结论与证据强度

发现一项被 0.2.3 放大的弹幕性能问题、两项既存界面性能问题。尚未复现或锁定“0.2.3 打开即全局卡顿”的唯一根因；不能据此将原因归结为核显性能或共享显存上限。

0.2.2（64de187）与 0.2.3（f331af1）的源码差异不涉及全局硬件加速、窗口材质、图片加载器、虚拟化面板或全局滚动驱动。新增共用手势仅作用于设置和消息模块；其滚轮计时器在收到输入后才启动。

## 1. 弹幕上限提高十倍，UI 处理没有对应预算（新版放大，已实测）

- `Services/ApiClient.cs` 和 `Views/Windows/PlayerWindow.xaml.cs` 把上限从 6,000 提到 60,000。
- `LoadDanmakuAsync` 在 Dispatcher 回调中再次排序并完成整表过滤；修改屏蔽设置也在 UI 线程遍历整表。
- `DispatchDanmaku` 的 while 循环一次处理全部已到时间的条目，没有每次派发的条数或耗时预算。
- `AddDanmaku` 先创建 Border、TextBlock、Transform，加入 Canvas 并 Measure，之后才由 `RenderRolling` 判断泳道是否可用。泳道满时控件仍然被创建、测量，再移除。同屏数量上限不能阻止这个路径，因为实际留下的条目很少。

对原始 0.2.3 发行包内的程序集运行同一时刻滚动弹幕突发夹具，每组重复三次：

| 条数 | UI 同步耗时 | 当前线程累计分配 | 实际留下条数 |
| --- | --- | --- | --- |
| 6,000 | 233–234 ms | 约 48 MiB | 5 |
| 60,000 | 1,887–2,258 ms | 约 480 MiB | 5 |

这是极端突发压力样例，不是普通视频每帧的负载，也不是“加载 60,000 条就必然冻结两秒”。480 MiB 是累计托管分配量，不是常驻内存或显存。它证实了在无可用泳道时仍做大量无效 UI 工作；新版提高总量后扩大了该问题的触发范围和最坏规模。

该问题不能独立解释未打开视频时的全局卡顿。修复应保留完整时间轴覆盖，同时限制单次派发工作量，并尽量在创建视觉对象前拒绝无位置的条目。

## 2. 加载圆环不可见、卸载后仍持续运行（旧问题，已实测）

`Views/Controls/LoadingRing.xaml` 的 Loaded 触发器启动无限旋转，但没有在不可见或 Unloaded 时停止。

确定性探针观察到：

- 正常显示时 `Rot.HasAnimatedProperties == true`，角度推进。
- 设为 Collapsed 后动画仍在，角度从约 217° 推进到约 343°。
- 从可视树移除后动画仍在，角度继续跨过一圈推进。
- 实际 MainWindow 从首页切到设置后，缓存首页的 5 个 LoadingRing 全部 `IsLoaded == false`、`IsVisible == false`，但 5 个旋转变换仍带动画。

因此隐藏和缓存页面仍保有持续计时的动画。这不是 0.2.3 新增；源码历史中至少已存在于 0.1.6 记录。对比停止这些时钟前后的空闲 CPU 样本有下降，但样本受预热和调度影响，不能将该差值当作稳定收益，也不能据此认定其单独造成用户所述严重卡顿。

修复方向：仅在 Loaded 且 IsVisible 时启动；不可见或卸载时移除动画时钟。应验证重新显示时恢复旋转。

## 3. 鼠标经过页头触发整条装扮背景重绘（旧问题，代码确认）

`MainWindow.xaml.cs:62` 在 PreviewMouseMove 中检测页头区域，排 Render 优先级回调并调用 `SharedHeaderSurface.InvalidateVisual()`。

`SkinSurface.OnRender` 的背景内容只依赖装扮、主题、位置及尺寸，没有读取鼠标位置，却会重新创建多层渐变、平铺画刷和不透明度遮罩。队列标记只能合并尚未执行的回调，不能避免鼠标移动期间反复重绘。该路径在 0.2.2 中已经存在。

独立夹具确认持续 InvalidateVisual 会产生额外渲染工作；“页头重绘”和“不重绘”样本不足以量化真实鼠标操作的收益。它是可去除的重复工作，尚不能作为全局卡顿唯一根因。

## 版本与验证方法

为避免只测试开发目录，直接读取两个便携发行包的 .NET 单文件 bundle，提取原始 `BiliTouch.dll`：

- 0.2.2 SHA-256：`02a72cbfbc322a49efe5c937b5835785f169923c7d43fc4e90b2fa3d8f2d1473`
- 0.2.3 SHA-256：`bec2aaef93676d5795e739b3bf207d58ec21aeb5a63d0a8631036302934bb04a`

开发测试输出中的 0.2.3 程序集哈希与发行包不同，所以发行包专项探针单独运行；不能把开发目录的通过结果直接算成发行包验收。

两版使用同一离线 API 夹具、相同窗口尺寸、相同 48/480 条视频数据，覆盖空闲、装扮、滚动、缓存页面切换和页头重绘。API 已替换为内存响应，封面 URL 为空，没有读取用户登录凭据或发起真实点赞等操作。原生 VLC 依赖复用本地测试目录。

测试进程报告 WPF rendering tier 2。两版普通界面样例没有发现 0.2.3 特有的持续布局循环。计时器延迟存在两版均出现的长尾，因此这些采样不能当作显示帧率，也不能据此宣称用户硬件上的流畅性。夹具不覆盖真实账户的大型关注列表、网络图片解码、高 DPI 的全屏像素负载或用户的驱动设置。

现有开发测试输出额外运行了触控板滚动 31 项、0.2.3 定向回归 33 项，共 64 项通过。它们是功能验证，不是用户所述卡顿的性能验收。
